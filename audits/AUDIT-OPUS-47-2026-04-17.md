## TL;DR

Projet techniquement ambitieux et architecturalement cohérent sur le papier, mais **la boucle auto-evolve produit aujourd'hui plus de cérémonie que de valeur** : 3390 règles CVE chargées, **22 actives (0,65 %)** ; les EIR "score 94 %→100 %" sont une auto-évaluation circulaire dont les rapports censés prouver le travail ne sont plus sur disque ; le feedback-loop Bayésien se valide sur des fixtures qu'il a lui-même produites. Côté hygiène, **un token Telegram en clair** traîne dans `.claude/settings.local.json` (644), 3 vulns `npm audit` dont 1 High dans le MCP du "security scanner", et le `deploy.sh` fait du `rsync --delete` sur `$HOME/.sentinel/` sans garde-fou. L'ossature reste saine ; le gros travail restant est de **dégonfler** (SKILL.md géants, 3291 règles vides, MCP tools fantômes) plutôt que de continuer à ajouter.

**Top 3 risques** : (1) auto-commit/push silencieux via `/sentinel-evolve auto` sur des données auto-générées non-vérifiées ; (2) KB polluée à 97 % qui fausse la RAG et les coûts de tokens ; (3) discordance docs↔code (MCP "2 tools actifs" vs 7 déclarés dans `src/index.ts`).

**Top 3 quick wins** : (1) retirer du `McpServer` les 5 tools non utilisés (`src/index.ts:26-187`) ; (2) supprimer/quarantiner les 3291 règles vides (`knowledge-base/domains/*/cve-rules.json`) ; (3) rotation du token Telegram + `chmod 600 .claude/settings.local.json`.

## Findings

### 🔴 Critical

#### C1 — Boucle d'auto-évolution circulaire, validation fictive
- **Fichiers** : `scripts/feedback-loop.py`, `scripts/rule-tester.py`, `tests/fixtures/{vulnerable,safe}/*`, `skills/sentinel-evolve/SKILL.md:36-77`
- **Effort** : 0,5-1 j (changement de doctrine, pas de code)
- **Problème** : Les 253 entrées de `knowledge-base/feedback/feedback.json` viennent toutes de `"project": "sentinel-fixtures"`, c'est-à-dire des fichiers `tests/fixtures/vulnerable/*` que l'équipe (toi) a écrits pour faire matcher les patterns LLM. Le `rule-tester.py` scanne ces fixtures, `feedback-loop.py seed` ingère les résultats, calcule des confidences Bayésiennes, puis propage cross-domain — sans qu'aucun signal externe (projet réel, audit humain, bug report) ne soit jamais entré dans la boucle.
- **Risque** : Les "scores de confiance 0,47→0,85" et "7 règles promues active" n'ont aucune valeur statistique — c'est un système qui se rate lui-même 10/10 puis s'en félicite. Les 22 règles "active" sont donc potentiellement des vraies règles OU des règles dont les patterns ne matchent rien de significatif en dehors des fixtures internes. Aucune garantie de precision sur du code réel.
- **Fix** : deux niveaux.
  1. Court terme : renommer la métrique pour ce qu'elle est — "fixture-precision" (pas "confidence"). Retirer "100 %" de tout affichage EIR (c'est trompeur). Ajouter dans `rule-tester.py` un avertissement explicite "uniquement validé sur corpus interne". 
  2. Moyen terme : intégrer un corpus externe (OWASP Benchmark, DVWA, NIST Juliet C/C++, ou les codes sources de 3-5 projets open source ayant des CVE connues) comme ground-truth. Sans ça, la pipeline CVE est un théâtre.

#### C2 — 3291 / 3390 règles CVE vides polluent KB, RAG et contexte
- **Fichiers** : `knowledge-base/domains/*/cve-rules.json` (100 726 lignes totales)
- **Effort** : 1-2 h
- **Problème** : Le `Bash` d'inventaire révèle `status: MISSING` pour 3291 règles (pas de `detect.patterns`, pas de `status`), `active: 22`, `no-matches: 70`, `needs-review: 7`. Soit **0,65 % d'opérationnel**. Ces règles vides sont quand même indexées par `rag/indexer.py` (→ les "4088 docs" sont truffés de NVD descriptions qui ne matcheront jamais rien) et sont chargées par les agents qui Read le `rules.json` de leur domaine.
- **Risque** : (a) coût token inutile sur chaque requête RAG ; (b) qualité de recherche dégradée — les 22 règles utiles sont noyées ; (c) quand un agent fait `Grep -n` sur `rules.json` de `supply-chain` (38 815 lignes), il charge ~1,5 MB de contexte pour 10 vraies règles.
- **Fix** :
  ```bash
  # Déplacer dans un staging, indexer une seule vue "active"
  python3 -c "
  import json, glob, os
  for f in glob.glob('knowledge-base/domains/*/cve-rules.json'):
      r = json.load(open(f))
      active = [x for x in r if x.get('status') == 'active']
      pending = [x for x in r if x.get('status') != 'active']
      json.dump(active, open(f, 'w'), indent=2)
      if pending:
          staging = f.replace('cve-rules.json', 'cve-rules.staging.json')
          json.dump(pending, open(staging, 'w'), indent=2)
      print(f'{f}: kept {len(active)} active, staged {len(pending)}')"
  # Ré-indexe : python3 rag/indexer.py
  ```
  Tant que les règles vides n'ont pas un pattern testé, elles n'ont rien à faire ni dans la KB ni dans la RAG. Garder le raw NVD dans `cve-feed/` si nécessaire pour la génération future, c'est tout.

Garder `generate-sbom` s'il est encore utilisé (à confirmer — je ne l'ai pas vu invoqué). Mettre à jour `package.json` si des deps deviennent inutiles. Rebuild : `npm run build`.

#### H1 — Token Telegram en clair, permissions lâches
- **Fichier** : `.claude/settings.local.json:9`
- **Effort** : 10 min (rotation + chmod + déplacement vers env)
- **Problème** : Le hook `Stop` contient `curl ... 'https://api.telegram.org/bot8529964004:AAFrlQyzcrl_0vbwopJzgXOmUrRRphLn0lc/sendMessage'` — token bot intégré dans la commande. Le fichier est `-rw-r--r--` (world-readable) et non tracké (git-ignored), mais reste en clair sur disque. Tout processus de l'utilisateur (y compris un npm script tiers) peut le lire.

  ```bash
  # 3. Réécrire le hook pour consommer $SENTINEL_TG_BOT_TOKEN au lieu de le hardcoder
  ```

  ```json
  "command": "[ -n \"${SENTINEL_TG_BOT_TOKEN:-}\" ] && curl -s -X POST \"https://api.telegram.org/bot${SENTINEL_TG_BOT_TOKEN}/sendMessage\" -d \"chat_id=${SENTINEL_TG_CHAT_ID}&text=Sentinel scan done\" > /dev/null 2>&1 || true"
  ```

#### H3 — `rsync -a --delete` sur `$HOME/.sentinel/` sans dry-run, destructif
- **Fichier** : `scripts/deploy.sh:62,71,88-92`
- **Effort** : 30 min
- **Problème** : 6 appels `rsync -a --delete` dont un sur `$SENTINEL_HOME/knowledge-base/`, `$SENTINEL_HOME/mcp-servers/`, `$SENTINEL_HOME/reports/`. Si un jour le repo source perd un sous-dossier (ex. branche WIP, commit partiel), le prochain `deploy.sh` supprime aussi la version en runtime. Les rapports générés en prod (EIR-*.json, SARIF archives) qui ne sont pas dans le repo source seraient donc wipés — ce qui est exactement ce qui se passe : `reports/archive/` en runtime ne contient pas les EIR cités.
- **Risque** : perte silencieuse de données runtime. L'absence des EIR-2026-04-* est probablement causée par ça (voir H4).
- **Fix** :
  1. Passer `reports/archive/` en sens inverse (runtime → repo) ou l'exclure du `--delete`.
  2. Ajouter un flag `--dry-run` par défaut et un `--apply` pour réellement exécuter :
     ```bash
     DRY_RUN="${DRY_RUN:-1}"
     RSYNC_OPTS="-a --delete"
     [ "$DRY_RUN" = "1" ] && RSYNC_OPTS="-a --delete --dry-run" && warn "DRY RUN — pass DRY_RUN=0 to apply"
     ```
  3. Exclure les artefacts runtime :
     ```bash
     rsync -a --delete --exclude='archive/EIR-*.json' --exclude='archive/*.sarif.json' "$PROJECT_DIR/reports/" "$SENTINEL_HOME/reports/"
     ```

#### M1 — SKILL.md géants vs cible Opus 4.7 (coût de contexte, pollution)
- **Fichiers** : `skills/security/SKILL.md` (661 lignes), `skills/sentinel-evolve/SKILL.md` (565 lignes)
- **Effort** : 3-4 h (réécriture structurée)

Ils contiennent 40 % de contenu *conditionnel/optionnel* (hooks v2.1.XX, modes audit/evolve/maintain, sections "Optional cross-validation", "Optional Plugin distribution"). Opus 4.7 suit très bien des instructions courtes/structurées en XML ou markdown strict, et son *effort: xhigh* lui permet d'inférer les détails sans qu'on les scripte. Plus on prescrit, moins il décide — et c'est parfois pire.
- **Risque** : chaque invocation du skill charge ~35 KB de contexte pour au final 10 % utilisé. Avec le tokenizer +35 % de 4.7, c'est ~12 000 tokens par appel rien qu'en skill.
- **Fix (before/after, exemple sur `skills/security/SKILL.md`)** :

  *Before* (lignes 116-162, ~48 lignes dense) :
  > "**Agent model tiers** — use the right model for each agent's complexity: [tableau]. **Security hardening** — set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`... **Cost monitoring** — Sentinel dispatches agents across multiple model tiers (haiku 4.5 for light... note: Opus 4.7's new tokenizer may use +35% tokens vs 4.6 — increase max_tokens headroom accordingly). **Progress tracking** — before dispatching, create a task..."

  *After* (~12 lignes) :
  ```markdown
  ### Agent dispatch
  
  Dispatch agents in parallel using `run_in_background: true`. Create one TaskCreate per agent for visibility.
  
  | Tier | Model | Agents |
  |------|-------|--------|
  | Heavy | inherit | web, api, llm-ai, supply-chain, mobile |
  | Medium | sonnet | database, infrastructure, data-privacy |
  | Light | haiku | cors, ssl-tls, static-site, websocket |
  
  Always exclude Write/Edit/NotebookEdit from agents (read-only audit). Use the agent file at `agents/{name}.md` for instructions and `agents/_protocol.md` for the execution contract.
  ```

  Objectif : **passer de 661 à ~250 lignes**. Sortir les sections "Optional / Plugin / OTEL / HTTP hooks / CI variations" dans des fichiers séparés lus à la demande, pas systématiquement.

#### M2 — Scoring "100 %" répété, pas de borne supérieure réaliste
- **Fichiers** : messages de commit depuis 2026-04-04, `skills/sentinel-evolve/SKILL.md:115-119`, `metadata.json`
- **Effort** : 2 h
- **Problème** : 4 EIR sur 5 récents terminent sur `100%`. Le score est calculé `USED / (USED + PARTIAL + NOT_USED) * 100`. Dès qu'un skill cite une feature dans un commentaire ou une table, `USED` passe à 1 — alors que *citer* ≠ *exploiter*. Résultat : le système félicite toute mention textuelle.
- **Risque** : KPI ornemental. La vraie question (est-ce que Sentinel *utilise effectivement* la feature dans son code de scan ?) est escamotée.
- **Fix** : basculer le scoring sur des preuves dynamiques. Ex : une feature `background_agents` compte `USED` seulement si au moins un appel `Agent(..., run_in_background: true)` a été observé dans les sessions des 30 derniers jours via `scripts/session-analyzer.py`, sinon `PARTIAL`. Borner à 85 % par construction ("100 % est suspect, pas un objectif").

#### M3 — Pas de tests automatisés exécutables en CI
- **Fichiers** : `tests/*.sh`, absence de `.github/workflows/` ou `ci/`
- **Effort** : 4 h
- **Problème** : `tests/e2e-session10.sh`, `test-sentinel.sh`, `test-session-analyzer.sh` sont des shell scripts non-idempotents qui supposent `~/.sentinel` déployé. Pas de pytest, pas de vitest, pas de CI. La regression se détecte quand Manuel relance manuellement.
- **Risque** : tout changement dans `scripts/*.py` passe sans filet. `pattern-gen.py parse_llm_output()` en particulier (regex-heavy) est le genre de code qui se casse silencieusement.
- **Fix (pragmatique, solo dev)** :
  1. Un seul `tests/test_scripts.py` (pytest) qui teste les 4 fonctions critiques : `parse_llm_output`, `prioritize_rules`, `load_empty_rules`, `load_kev_cve_ids` — ~1 h.
  2. Un seul `.github/workflows/ci.yml` qui run `pytest tests/` + `npm run build` dans `mcp-servers/sentinel-scanner/` + `shellcheck scripts/*.sh`. Limite à 3 min. Ajoute `actions/setup-python` + `actions/setup-node`. ~1 h.
  3. Pre-commit hook local `.git/hooks/pre-commit` qui lance les tests Python avant push (c'est sufisant pour un solo).

#### M4 — Pas de rotation de logs, accumulation silencieuse
- **Fichiers** : `.claude/skill-audit.log` (22 KB), `~/.sentinel/logs/` (non visible)
- **Effort** : 30 min
- **Problème** : `.claude/skill-audit.log` grossit à chaque audit de skill sans rotation. `~/.sentinel/logs/agent-failures.log` et `compaction.log` (configurés dans `settings.json:13-33`) idem.
- **Fix** : ajouter un cron local (ou hook `SessionStart`) `find ~/.sentinel/logs -name "*.log" -size +10M -exec mv {} {}.$(date +%Y%m%d) \;` + `gzip`. Ou plus simple : `logrotate` avec conf `~/.sentinel/logrotate.conf`.

#### M5 — Règles incohérentes : CLAUDE.md rule bloque skill-audit sur *tous* les CLAUDE.md du système
- **Fichier** : `memory/feedback_skill_audit_hook_fix.md` (d'après l'index memory)

Le hook SessionStart actuel (`PreToolUse:Bash`) suggère encore de lancer skill-audit avant d'installer un skill — si la règle n'a pas été complètement annulée, des false positives peuvent encore apparaître.

## Positionnement produit (non-audit, à prendre ou laisser)

Sentinel est à la croisée de trois choses :
1. **Un terrain d'expérimentation méta** pour Manuel (comment on construit un skill complexe avec KB/RAG/MCP/agents).
2. **Un outil d'audit qu'il utilise vraiment** sur ses autres labs.
3. **Un candidat plugin distribuable** (`sentinel-plugin/`).

Le (1) justifie tout ce qu'on a. Le (2) est réaliste : 22 règles bien testées + `scan-dependencies` (OSV) + `scan-headers` couvrent déjà le gros des besoins pour un scan léger de ses propres projets. Le (3), honnêtement, est *premature*. Un utilisateur externe, face à un outil qui git-push tout seul, avec 3300 règles vides, des scores auto-100 %, et une dépendance au `claude -p` d'un abonnement Max, va fuir. **La conclusion que je tirerais : stopper de chercher à devenir un produit, et assumer Sentinel comme un lab privé premium. Si un jour le packaging redevient actuel, la barre minimum est "corpus externe validé, scoring honnête, sans auto-commit".**
