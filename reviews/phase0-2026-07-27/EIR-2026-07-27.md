## 2. Le constat central : un score qui ne pouvait pas baisser

L'EIR du 10/06 affichait un score d'exploitation de **98 %**. Ce chiffre était calculé sur `feature-inventory.json`, **figé à 188 entrées depuis le 10/06** alors que 41 releases ont été publiées depuis.

Le score n'a pas baissé parce que **le dénominateur n'a pas bougé**. Recalculé sur la surface réelle de v2.1.220, le taux d'exploitation tombe à **≈ 84 %**.

C'est le défaut le plus structurant du cycle : le mode `analyze` — et par ricochet le mode `audit` qui note tous les autres projets — mesure Sentinel contre un référentiel de juin. Tant que REC-006 n'est pas appliquée, tous les scores produits par ce skill sont flatteurs par construction.

Le pipeline de collecte, lui, fonctionne : les crons ont bien rapatrié les données brutes ce matin même (07:00). C'est la **couche d'analyse** qui n'a pas suivi, pas la collecte.

## 3. Finding bloquant — drift runtime → repo inversé

Le workflow documenté dans `CLAUDE.md` est : *éditer dans le repo, puis `deploy.sh` vers `~/.claude/skills/`*. Ici, c'est l'inverse qui s'est produit.

Les corrections Opus 5 du **25/07** ont été écrites **directement dans le runtime** et n'existent pas dans le repo :

| Élément | Repo (source de vérité) | Runtime (`~/.claude/skills/`) |
|---|---|---|
| `effort` de sentinel-security | `xhigh` | `high` ✅ |
| Tier « Light » | `haiku` | `sonnet` ✅ (doctrine 19/07) |
| Modèle orchestrateur | pin littéral `Opus 4.8` | alias `opus` ✅ |
| Classifieurs Opus 5 renforcés | absent | documenté ✅ |
| Filtres de sévérité suivis littéralement | absent | documenté ✅ |
| Paths des agents | `skills/security/` | `skills/sentinel-security/` ✅ |
| Section Opus 5 (evolve) | absente | complète ✅ |

**`bash scripts/deploy.sh` exécuté maintenant détruirait l'intégralité de ces corrections.** J'ai donc arrêté le pipeline avant l'étape 6. La réconciliation doit se faire runtime → repo (REC-001), et seulement ensuite le déploiement peut reprendre son sens normal.

Effet de bord constaté : le déploiement est par ailleurs **incomplet** — `~/.claude/skills/sentinel-rag/` n'existe pas du tout (skill non invocable), et `~/.claude/skills/sentinel-evolve/` ne contient que `SKILL.md`. Cela explique la note portée en runtime le 25/07 affirmant à tort que « `scripts/deploy.sh` n'existe pas » : vu depuis `~/.claude/skills/` seul, il est effectivement invisible — il est bien présent dans le repo (`scripts/deploy.sh`, 15 Ko).

## 4. Erreurs factuelles dans les skills

Deux affirmations du `SKILL.md` de sentinel-security sont devenues fausses :

- **Ligne 82** — « Use an **Explore subagent** (Haiku-based, fast and cheap) ». Faux depuis **v2.1.198** : l'agent Explore intégré hérite désormais du modèle de la session principale (plafonné à `opus`) au lieu de tourner sur Haiku. L'étape de détection de stack coûte donc bien plus cher que ce que le skill annonce. *(REC-002)*
- **Lignes 128-132** — raisonnement sur « haiku 4.5 / sonnet 4.6 / Opus 4.8 ». Sonnet 5 est le défaut CC depuis **v2.1.197**, Opus 5 le défaut Opus depuis **v2.1.219**. *(REC-003)*

À noter également : `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` est posé dans l'environnement de cette machine et **écrase les `model:` par agent** — la table de tiers du SKILL.md est donc indicative tant que cette variable est en place.
